# Native volume controls — issue #151

This local implementation follows the preserved `7ba4654` player baseline.
Local compilation and agent review do not establish physical or release acceptance.

## Ownership and public APIs

On iPhone/iPad, a visible `MPVolumeView` owns output-volume interaction. The
SwiftUI wrapper constructs the native view and has an empty update method. It
does not subclass MPVolumeView, inspect its subviews, replace its adjustable
accessibility elements, bind `outputVolume`, forward synthetic slider events,
activate audio sessions, or perform requests. The 44-point allocation must still
be checked with actual finger input and VoiceOver on the device.

The native view handles supported, fixed and unavailable route volume. Keep its
route-button default: `showsRouteButton` is deprecated, and this project treats
compiler warnings as errors. Do not suppress that warning or hide a private
subview. The separate `AVRoutePickerView` remains the app's route control; report
any duplicate native route affordance during physical testing.

On Mac, the visible **Player volume** slider changes only the existing AVPlayer's
0...1 gain. Nonfinite values are ignored and finite values are clamped. AVPlayer
remains the authority; there is no second volume model, system-volume API, audio
session change, persistence setting or playback/queue transition in the setter.

## Verification

Focused Mac coverage checks finite/clamped gain, retained playback ownership,
no added resolver/session work and preservation across queue replacement. Compile
both platform branches, run lint and check the scoped diff. These are local gates.

Physical acceptance remains separate: direct iPhone touch (Mirroring alone is
insufficient), hardware buttons and Control Center agreement, supported/fixed
routes, AirPlay connection/return, accessibility, repeated Now Playing reopening,
volume changes during skips/history/background playback, and zero added API or
artwork requests from control redraws or adjustments. Mac acceptance must confirm
this app's audible gain changes without claiming a system-volume change. Record
exact source/toolchain/device/route and failures before resets.

## Primary references

- [MPVolumeView](https://developer.apple.com/documentation/mediaplayer/mpvolumeview): native system-output UI and supported public appearance API.
- [AVPlayer.volume](https://developer.apple.com/documentation/avfoundation/avplayer/volume): player gain; Apple's SDK explicitly directs iOS end-user volume to MPVolumeView.
- [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#software-requirements): 2.5.1 requires public APIs used for intended purposes; 2.5.9 protects standard hardware-control behavior. The design does not intercept or remap hardware controls; the observed volume-jump defect still requires investigation.
- [Apple Developer Forums thread 820665](https://developer.apple.com/forums/thread/820665): the final August 2026 DTS clarification identifies MPVolumeView as the public system-volume UI. Earlier March replies incorrectly conflated it with route selection; they do not justify replacing volume with AVRoutePickerView or manipulating UISlider internals.

These sources support the implementation boundary, not an App Review approval
guarantee or a claim that every output route supports variable volume.

## 0.3.5 disposition

Initial device checks did not cover Control Center changes followed by the next
in-app or hardware adjustment. That sequence later produced an audible jump.
The owner explicitly accepted shipping the slider with this unresolved defect;
see [known issues](0.3.5-known-issues.md). Native API use is not proof of correct
combined behavior.
