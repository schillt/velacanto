# Velacanto 0.2.5 stabilization release notes

## Purpose

0.2.5 packages the physically accepted playback, network-admission, queue, and
session-restoration candidate as one provenance-controlled internal build. It
exists to give 0.3 development a reliable listening foundation without
reopening playback architecture or adding unrelated UI and performance work.

The final release commit will be recorded after the accepted source, version
and release-documentation changes, and the DEBUG-only test isolation repair
pass the required gates. The repair resets the shared network-policy singleton
between tests and updates stale harness expectations; the Release configuration
retains its process-lifetime singleton and accepted runtime behavior.

The hosted OS 27 gate also exposed stale UI-test assumptions about native
navigation-bar accessibility plus a cold-simulator launch race. The release
harness now runs iOS units before the UI target, keeps UI execution serial, and
asserts stable user-visible content instead of framework-generated navigation
containers. No application behavior is changed and every unit and UI test
remains required.

## Included stabilization

- Preserves the active queue, current cursor, elapsed position, and intent
  ownership through pause, navigation, cancellation, recovery, and relaunch.
- Makes latest playback intent win during rapid Next and direct queue selection
  without stale adoption, overlapping player ownership, or destructive queue
  replacement.
- Keeps player replacement readiness-gated and makes recovery failure bounded
  and retryable.
- Separates playback-critical network admission from background reporting and
  other non-playback work so ancillary activity cannot degrade the active
  playback route.
- Restores saved Jellyfin sessions and persisted playback state while retaining
  privacy-safe diagnostics and account isolation.
- Adds focused deterministic playback/network/session regression coverage.

- A simplification audit found only negligible unused/nil-forwarding cleanup;
  it is deferred so the accepted candidate is not changed for cosmetic reasons.

## Accepted limitations and follow-up

- One successful Play Next load took about 10.2 seconds; other successful
  selections converged in about 3.2 and 2.1 seconds. This is accepted
  performance debt tracked in issue #47, not justification for another 0.2.5
  behavior change.
- Queue reordering is not currently functional and is excluded from 0.2.5
  acceptance. Play Next and direct History/Up Next selection are accepted;
  reordering remains tracked in issue #12.
- 0.3 UI, accessibility, system-media, real-server, and final promotion work
  remains governed by issues #63 and #65 and the documented
  `alpha → beta → preview → main` path.

## Distribution boundary

0.2.5 is an internal stabilization build. Internal TestFlight distribution is
permitted by ADR 0010 after the exact candidate passes local and hosted gates.
External testing, App Review submission, and public App Store release require
separate owner authorization and are not part of this release record.
