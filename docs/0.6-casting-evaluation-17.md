## Contract and proposed decision

The [live issue](https://github.com/schillt/velacanto/issues/17) and its one
[comment](https://github.com/schillt/velacanto/issues/17#issuecomment-5667024670)
were read through the authenticated GitHub connector, including all comment
pages, on 2026-10-26. Its 0.5 disposition deferred broader casting and distinguished
native AirPlay. The historical disabled-placeholder description refers to 0.3;
it does not describe the reviewed source. The current
[0.6 plan](0.6.0-plan.md#phase-4--resolve-the-two-evaluation-contracts) requires an
inventory and a ship/defer/reject decision; a prototype is conditional on value.
It explicitly does not require an additional casting protocol to ship in 0.6.

**Recommendation for owner selection:** retain the existing native AirPlay route
on iOS/iPadOS and macOS for 0.6; reject a generic cross-protocol casting framework
for this implementation; defer additional protocols until a specific receiver
and user outcome justify their scope. This is a proposed product decision, not
an owner-approved milestone move. AirPlay itself still needs applicable physical
route acceptance. No source defect justifies a new native UI slice here: the
route control already exists on both platforms.

If broader casting is selected, the smallest next investigation is Jellyfin
remote control of an already authenticated, controllable disposable client
session. That avoids raw LAN discovery and third-party sender integration, but
still needs a separate remote-session ownership contract and server acceptance;
it is not an AVPlayer output route. Do not implement it as an invisible alternate
meaning of the current AirPlay button.

## Available options and constraints

| Option | Public support | Prerequisites, gaps and proposed disposition |
| --- | --- | --- |
| Native AirPlay audio | Apple AVKit/AVFoundation on both maintained platforms. | Existing implementation. Keep OS route selection and the existing player; no receiver app, custom transport or app-owned LAN scan. Proposed 0.6 scope. It does not promise Chromecast-only/DLNA receivers or playback independence after sender termination. |
| Google Cast | Google documents iOS, Android and Web senders, plus receiver apps; no native macOS sender SDK in that supported-platform list. | iOS requires a new sender/session integration and consent flow. Native Mac parity is unestablished; a browser sender is a different product surface. Defer pending an actual receiver target and explicit platform decision. [Google overview](https://developers.google.com/cast/docs/overview). |
| Jellyfin Cast receiver | Jellyfin maintains a Cast Web Receiver, used by its Android and Web clients. | Existence does not establish VelaCanto sender compatibility or permission to reuse its production receiver identity. Need protocol/authentication, receiver reachability, version and control-ownership validation. No receiver registration or credential transfer is authorized by this evaluation. [Jellyfin receiver](https://github.com/jellyfin/jellyfin-chromecast/blob/master/README.md). |
| Jellyfin remote client control | Authenticated server `GET /Sessions` supports a controllable-user filter; session play/control endpoints dispatch instructions. | Candidate for a separately selected minimal investigation on either platform. Require server-authorized target, advertised capabilities, stale/disconnected target handling and confirmation of remote execution. HTTP success is not audible execution. No app-owned multicast discovery is needed for this server-mediated approach. [Jellyfin SessionController](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/SessionController.cs). |
| DLNA/UPnP | Jellyfin DLNA is a separately installed first-party plugin since server 10.9, using SSDP UDP1900. | A server plugin is not an implemented VelaCanto renderer controller or universal receiver compatibility. Direct iOS SSDP introduces multicast approval and local-network consent; server-mediated alternatives need their own server/plugin verification. Reject raw discovery in this slice; defer product support. [Jellyfin DLNA](https://jellyfin.org/docs/general/post-install/networking/dlna/). |
| Bluetooth/wired/system output | Output selection belongs to platform routing. | Retain native/system behavior; not a new casting protocol or entitlement. Handoff and CarPlay retain their separate contracts. New music providers #18/#21 are outside #17. |

Apple's [media configuration guidance](https://developer.apple.com/documentation/avfoundation/configuring-your-app-for-media-playback)
requires the playback session and background-audio mode for the relevant iOS
background/AirPlay behavior, with activation deferred until playback. Current
source has these components. There is no evidence here requiring an additional
AirPlay-specific entitlement or changing valid stable credential entitlements.

Apple [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)
distinguishes system AirPlay, which isolates local-network details and needs no
app local-network access, from app-owned Bonjour/network operations. iOS raw
multicast/broadcast requires the separately approved
[multicast entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.multicast).
Do not infer that Bonjour always requires multicast approval or that the existing
personal-server LAN permission grants a new discovery purpose. Mac sandbox
network permissions and OS local-network consent are separate checks.

Google's [iOS discovery guide](https://developers.google.com/cast/docs/ios_sender/permissions_and_discovery)
requires local-network purpose text and Cast Bonjour service declarations for
modern sender integration, with user-initiated discovery supported. It explicitly
does not prescribe obtaining multicast approval solely for modern Cast support.
[Registration](https://developers.google.com/cast/docs/registration) is required
for styled/custom receivers; Google's Default Media Receiver is an exception.
That exception does not establish authenticated Jellyfin compatibility.

Receiver-fetch playback must establish its own server reachability, HTTPS,
authentication, redirect and media compatibility; sender playback success cannot
prove those. Google's [media guide](https://developers.google.com/cast/docs/media)
documents codec/device differences and CORS requirements for adaptive streams.
Do not expose a private origin or session token to test generic receiver playback,
change server networking, add an app proxy or copy a credential-bearing AVPlayer
URL to an arbitrary receiver. Existing [#25 URL risk](playback-url-privacy.md)
remains open; this evaluation neither proves nor excludes AirPlay URL exposure.

Background remote control is not equivalent to local background audio. Google
documents background session suspension enabled by default in
[GCKCastOptions](https://developers.google.com/cast/docs/reference/ios/interface_g_c_k_cast_options).
A new sender must handle return/reconnect, stale receiver state and explicit
disconnect without faking local playback or adding silent audio to stay alive.
Apple [review guidelines](https://developer.apple.com/app-store/review/guidelines/)
2.5.4 restrict background modes to their intended purpose; third-party SDK/data
sharing disclosures and complete review access also need assessment before
distribution. No approval or store-compliance result is claimed.

## UX parity and acceptance gaps

The current implementation provides a native route chooser on both platforms;
the app does not maintain its own selected-receiver name, discovery spinner,
permission recovery, remote queue or reconnect state. These are not proven
AirPlay defects: the OS picker/system controls own route presentation. Confirm
physical behavior before adding duplicated route state. Native Mac gain and
iOS system volume are intentionally different; neither proves receiver volume
parity. The iOS picker uses white tint within the expanded player; actual contrast,
active-route indication and VoiceOver/keyboard interaction remain visual and
assistive-technology checks, not findings inferred solely from source.

Before claiming route acceptance, the coordinator should obtain an exact signed
candidate and an owner-authorized compatible receiver/disposable media scope.
Record platform/build, receiver class without stable identifiers, ordered actions,
debugger/Mirroring state and owner-confirmed audible results:

1. Open picker with no receiver, cancel, and confirm current playback is unchanged.
2. Explicitly connect while playing; verify sound, native route indication,
   pause/resume/seek/next, queue advancement and metadata/system controls.
3. Lock/background and return; disconnect or lose the receiver; verify honest
   state and intended local resumption without duplicate playback.
4. Exercise streaming quality/direct/HLS and retained downloads where affected,
   plus playback while browsing/expanding Now Playing under the protected-loading
   contract. Do not assume downloaded-file routing equals remote-stream routing.
5. Verify iPhone/iPad touch/VoiceOver and Mac keyboard/VoiceOver/native volume
   behavior, including unavailable destinations and permission denial for any
   newly selected discovery protocol.

These are pending checks, not requests to run them without serialized lane and
owner scope. Source review and existing synthetic Now Playing/player tests cannot
establish AirPlay audibility, receiver auth handling or real casting.
