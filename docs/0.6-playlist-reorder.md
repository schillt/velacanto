## Shared behavior and boundaries

`FoundationPlaylistReorderSheet(playlist:library:)` is one native component for
both iOS and macOS. It shows the complete server membership snapshot, including
repeated track occurrences, rather than applying search or album-version display
projections to the indices used for a mutation. SDK27's native reorder container
uses stable membership IDs; ambiguous snapshots use distinct local row IDs and
remain read-only, so repeated server identities cannot collapse visible songs; native Move Up/Move Down actions provide another
accessible path. It reuses the existing playlist artwork/music row, sheet size
and native feedback presenter. #64 owns shared management/detail/sidebar entry
points; their hook commits are separate dependencies.

One shared mutation path checks current edit permission and loads a fresh bounded
membership snapshot before writing. The expected membership order and track
identities must still match. Selected occurrences retain their source order,
including noncontiguous selections around the destination. Moving a single song
from the start to the end sends one membership move, rather than moving every
intervening song. The generated Jellyfin SDK endpoint uses the membership entry
ID and final zero-based position. Its server implementation is reviewed at the
[primary source](https://github.com/jellyfin/jellyfin/blob/master/Emby.Server.Implementations/Playlists/PlaylistManager.cs).

After the moves, another complete snapshot must match the requested order before
success is published. The HTTP acknowledgement alone cannot establish success.
The API does not supply an atomic revision precondition: concurrent edits between
preflight and confirmation remain possible and must produce an unconfirmed
outcome rather than an invented transaction guarantee.

While a request is pending the proposed order is shown and further moves are
disabled. Error or cancellation leaves the order explicitly unconfirmed and
requires Refresh before another move. Some sent moves may have reached the
server. No automatic write retry or compensating rollback is attempted; a
concurrent membership must never be erased to force the desired result. Existing
account-owned playlist invalidation and download reconciliation are reused.
Up Next, current/history identity, player ownership and audio transport are not
modified by this feature.
