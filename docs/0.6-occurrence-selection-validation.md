Implementation base: `8d69179180f5f549d012ec11614e98c180e63080` (beta merge),

No version/build, player, transport or loading-admission policy is changed.

## Change

`FoundationTrackQueueSelection` projects already-loaded track occurrences with
an explicit availability predicate. It rejects invalid source positions,
non-track selections and unavailable selections. Retained ordering and the
selected index follow source positions, including repeated copies of the same
track ID; the helper performs no remote read, identity deduplication or state
mutation.

The browse-model and favorite-selection entry points use the same projection.
Favorites additionally apply existing authoritative display membership; offline
callers additionally apply existing ready-download availability. Filtering never
rewrites the source page or its pagination cursor.

## Caller inventory

| Entry point | Shared row-selection behavior |
| --- | --- |
| Home recent songs | Loaded browse-model tracks and current offline availability |
| New tracks | Loaded browse-model tracks; display preview limit does not truncate the prepared loaded queue |
| Favorite shelf | Existing favorite display predicate plus availability |
| Catalog/search category rows | Loaded tracks, optional favorite predicate and availability |
| Library typed index | Currently displayed loaded model, including explicit search/alphabet range |
| Artist suggested songs | Loaded suggestion model plus availability |
| Album/playlist track rows | Existing expected row/membership identity validation remains before selection; album canonical-copy fallback remains unchanged |
| Search discovery/top results | Supplied result sequence plus availability, remapped by occurrence rather than first matching track ID |

The Search path previously selected the first matching track ID after filtering.
With repeated IDs, that can map a later tapped occurrence to an earlier one. The
shared source-position policy removes that mismatch; this is a source-backed
correction, not a claimed reproduction with a user's library.

Explicit full-collection Play/Shuffle is intentionally different: it resolves a
collection or uses its verified local tracks and starts the resulting sequence,
rather than mapping a tapped loaded row. Shared item-menu collection actions,
Siri and CarPlay preserve their existing request/commit guards. Existing Up Next
selection uses queue occurrence UUIDs and is outside this projection. Native
player ownership, playback resource resolution and admission remain intact.
